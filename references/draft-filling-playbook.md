# 两份软著草稿的可复用填报知识

这份手册沉淀服务端、桌面端两类软著在中国版权保护中心 R11 页面上的共同操作规则。它只指导材料和草稿操作，不代替申请人核对事实，也不允许 agent 点击“确认填报”或正式提交。

## 1. 先区分三种完成状态

不要把下面三件事合并成一个“已完成”：

| 状态 | 证明材料 | 含义 |
| --- | --- | --- |
| 材料已生成 | PDF、DOCX、`auto-fill/config.json` | 本地文件可用 |
| 网页已填写 | 页面回读 JSON | 页面字段与基线一致 |
| 草稿已保存 | 草稿保存提示、时间、草稿号（若页面显示） | 网站已保存，但不代表已正式提交 |

每份草稿保存后都应记录一份不含密码、验证码和令牌的回执：

```json
{
  "status": "saved_draft",
  "softwareName": "软件全称",
  "version": "V1.0",
  "programPdf": "AI 协作-后端源码.pdf",
  "docPdf": "AI 协作-后端软件说明.pdf",
  "savedAt": "2026-09-22T12:00:00+09:00",
  "draftId": "页面显示时填写；未显示则留空"
}
```

网页回读仍以 `form_plan.py --verify` 为准；回执只是保存结果记录，不能替代确认页核对。

## 2. 一份项目配置对应一份草稿

服务端、桌面端、移动端即使属于同一产品，也必须各自有独立的：

- `projects[]` 配置和项目 id；
- 软件全称、简称、端类型和功能边界；
- 源码文件清单与源码统计；
- 说明书 Markdown、PDF 和申请表配置；
- 浏览器上传材料路径。

共同的产品术语可以复用，例如“工作区、任务、智能体、运行时、实时同步”；功能段落、源码文件和证据不能直接复制。服务端描述 API、权限、数据库、租约和实时中继；桌面端描述窗口、导航、页面控件、本地守护进程和用户操作。

## 3. 端类型决定证据模板

在 `projects[]` 中设置 `artifact_label`，文件名和证据清单据此生成：

```json
{
  "short_name": "AI 协作",
  "artifact_label": "后端",
  "document_kind": "backend"
}
```

| `artifact_label` | 文件名示例 | 主要证据 |
| --- | --- | --- |
| 后端 | `AI 协作-后端源码.pdf`、`AI 协作-后端软件说明.pdf` | 成功响应、参数错误/4xx、启动或业务日志；实际启用 Knife4j/OpenAPI 时再加调试页 |
| 桌面端 | `AI 协作-桌面端源码.pdf`、`AI 协作-桌面端软件说明.pdf` | 任务、项目、智能体、聊天、设置、运行时等真实界面截图 |
| 移动端 | `AI 协作-移动端源码.pdf`、`AI 协作-移动端软件说明.pdf` | iPhone/iPad 模拟器、真机或移动端浏览器中的真实页面 |
| 小程序 | `AI 协作-小程序源码.pdf`、`AI 协作-小程序软件说明.pdf` | 微信开发者工具模拟器和真实交互结果 |

程序材料和文档材料不能只看目录位置判断，必须同时核对软件简称、端类型和材料后缀。

## 4. 浏览器填报固定节奏

1. 用户本人登录并确认著作权人账户；agent 不输入账号、密码或验证码。
2. 通过页面结构和可见 label 定位控件，不使用固定坐标，不依赖固定 tab id。
3. 每一步先填值，再失焦，再回读关键字段，确认无误后才点“下一步”。
4. 长文本从 `auto-fill/长文本/mainFunction.txt` 整段粘贴，回读页面字数；不要手打或在两套自动化工具中重复输入。
5. 日期选择后按 `Esc` 关闭日期面板，再读取日期输入框。
6. 文件上传使用可见上传卡片触发文件选择，等待 `100% + 文件名`，再继续。
7. 上传失败先检查页面是否已经有同名文件，确认没有成功后再重试。
8. 到确认页后，至少回读软件全称、简称、版本、日期、发表状态、著作权人、源程序量、主要功能字数和两个 PDF 文件名。
9. 回读全部通过后只点击“保存至草稿箱”，保持浏览器打开，交给用户本人最终提交。

## 5. 上传前材料检查

生成 PDF 和 `auto-fill/config.json` 后运行：

```bash
python3 scripts/artifact_manifest.py \
  --config soft-copyright-materials/ruanzhu.config.json \
  --project <项目 id> --verify --strict
```

工具生成项目目录下的 `材料上传清单.json`，核对：

- 端类型和文件名前缀是否一致；
- 程序 PDF 和文档 PDF 是否为两个不同文件；
- 文件是否存在；
- 程序材料页数是否达到配置的 `source_pages`；
- `auto-fill/config.json` 中的 `programPdf`、`docPdf` 是否指向当前文件名；
- 文件大小、页数和 SHA-256，方便发现上传了旧版本。

文件重命名后不能只改文件本身，必须重新运行 `application_form.py` 和 `form_plan.py`，让申请表文案、操作计划和上传路径一起更新。

## 6. 截图和后端证据的一致性

有界面的项目把 `截图清单.json` 作为唯一事实源。每张图应有唯一编号、模块、标题、源文件和正文引用；正文、附录和 PDF 不应手工维护另一套文件名。

后端项目没有独立业务页面时，说明书可以明确写“本版本不提交独立页面截图”，但应补真实 API/日志证据计划。不得用模板页面或伪造 JSON 代替实际运行结果。

## 7. 保存草稿前的最终闸门

- 配置和网页都没有占位符；
- 软件全称、简称、版本在说明书、申请表和 PDF 中一致；
- 著作权人和开发完成日期已由申请人确认，不能从另一份软著自动复制；
- 主要功能为 500–1300 字，技术特点不超过 100 字；
- 源程序量是全项目统计，不是 60 页取材行数；
- AIGC、版权风险和源码脱敏检查已完成；
- 两个 PDF 的文件名、端类型、页数和网页上传卡片一致；
- 只保存草稿，不执行正式提交。

## 8. 这两类项目常见的可复用故障

| 故障 | 原因 | 处理 |
| --- | --- | --- |
| 网页上传了旧文件 | 文件重命名后 `auto-fill/config.json` 未重生成 | 运行 `artifact_manifest.py --verify --strict`，再重跑申请表脚本 |
| 桌面端仍出现“待确认” | 本地配置和网页草稿不是同一份基线 | 以网页确认页回读为准，并把确认值同步回项目配置 |
| 截图在目录但 PDF 看不到 | 截图清单、正文引用或渲染输入不一致 | 先检查 `截图清单.json`，再重新生成 Markdown 和 PDF |
| 点下一步没有跳转 | 字数、日期或选择项校验失败 | 先读取页面红色提示和计数器，不要反复点击 |
| 上传重试后出现两份文件 | 没有先确认第一次是否成功 | 先回读上传卡片和文件名，再决定是否重试 |
