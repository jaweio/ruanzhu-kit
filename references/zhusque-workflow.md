# 朱雀增量检测与复核

本流程使用腾讯 `zhuque-text` API 或朱雀官方网页。`aigc_check.py` 的本地规则分数与这两种真实检测结果分开记录，不能互相替代。检测标签描述服务对文本的判断，不证明作者身份。

本流程由执行 ruanzhu-kit Skill 的当前 agent 在同一任务中编排，不依赖独立 App。脚本处理分块、请求、缓存与校验；浏览器操作失败后，当前 agent 接着调用宿主的 Computer Use。内部“交接”指脚本与 agent 之间的状态传递，不要求用户复制任务或另开会话。

## 1. 授权和检测范围

用户明确要求检测选定材料后，授权覆盖本轮 API 请求、官方网页回退和改写后的复核；不逐块重复询问。扩大材料范围或换用其他服务时再确认。CLI 每次启动仍须带 `--allow-upload`，避免脚本被误调用时发送正文；此参数不要求对已经授权的工作再次提问。

用户已明确允许本轮 Computer Use 点击操作时，该授权继续有效，agent 不再要求重复确认。**验证码和登录一律由用户本人完成**：agent 不识别、不拖动、不点选验证码，也不输入账号信息；出现时停下，请用户在已打开的窗口完成，用户告知完成后再续检。

对每份软著材料目录分别运行。目录模式读取当前 `软件说明书.md`、`申请表填报文案.md`、`auto-fill/config.json` 的长文本，以及 `材料上传清单.json` 指定的文档 PDF；没有清单时使用兼容的说明书 PDF 文件名。源码 PDF、章节副本、历史目录、截图证据计划和内部检查报告不递归送检。需要只测某份文件时，显式传入该文件；局部检测不能当作整个材料目录完成。

发送前核对选定文本及已有脱敏结果。API Key 只从本机环境变量 `MAKERS_MODELS_KEY` / `RUANZHU_ZHUSQUE_API_KEY`、macOS Keychain 或 App 加密设置读取，不写入项目配置、报告或命令参数。TypeSafe/Jev Key 不能用于腾讯朱雀。

## 2. 先看计划，再执行或续检

```bash
# 不联网、不打开浏览器，只写待检清单并显示字符量
python3 <skill目录>/scripts/zhusque_check.py finalize <材料目录> --plan

# 首轮和修改后使用同一命令；已有结果自动复用
python3 <skill目录>/scripts/zhusque_check.py finalize <材料目录> \
  --allow-upload --channel auto --report <材料目录>/朱雀检测报告.md

# 指定渠道
python3 <skill目录>/scripts/zhusque_check.py finalize <材料目录> --allow-upload --channel api
python3 <skill目录>/scripts/zhusque_check.py finalize <材料目录> --allow-upload --channel web

# 明确需要重新请求全部当前单元时，忽略缓存及网页已有结果
python3 <skill目录>/scripts/zhusque_check.py finalize <材料目录> --allow-upload --no-cache
```

`auto` 优先使用已配置的 API；无 Key 或 API 失败时切换官方网页。同一轮不反复重试已经失败的 API。网页接管、定位或点击失败以及出现验证码时，由宿主 agent 按第 3 节尝试 Computer Use 兜底。`api` 只使用 API，`web` 只使用网页；Computer Use 属于网页操作方式，不是第三种检测模型。尚未取得对应结果的单元始终为 pending，不能因切换操作方式就记为检测成功。

首轮为全部当前正文建立覆盖。分块尽量保留段落、标题和相邻上下文，目标约 700 字符、默认上限 2,000 字符；长段落局部拆分，短段落尽量与附近原文合并，不补写文字凑检测长度。`--max-chars` 可调整上限；网页当前要求超过 350 字，过短且无法合并的材料会明确阻塞。

后续缓存按实际提交的相同文本、渠道/模型及分块设置匹配。进度文件还保存块的短前缀哈希与全文哈希，用于在新增、删除文字后寻找仍未改变的原有块；不因开头短段变长就把后续全文重新分组。改动块和分段边界受影响的相邻上下文会重新检测，未受影响块复用历史有效结果。同一单元在多个位置出现可复用，但 Markdown 与 PDF 提取文本常有空白、标点、页码等差异，不能保证它们完全命中同一缓存。改变分块配置或删除进度文件也可能增加请求量。

缓存默认位于 macOS 的 `~/Library/Caches/ruanzhu-kit/zhusque`，保存分类、位置、用量和来源等结果，不保存原文或 Key。材料目录中的改写任务单和网页证据会包含正文，属于内部复核件。

## 3. 网页、Computer Use 兜底与恢复

网页驱动需要已安装的 Chrome、Node.js 和 Playwright。脚本查找已安装模块，也支持 `RUANZHU_PLAYWRIGHT_PATH`；不要求安装桌面 App。Chrome 使用本机安装路径，也可通过 `RUANZHU_CHROME_PATH` 指定。驱动不会自动下载浏览器。实际入口为 `scripts/zhusque_browser.py` 和 `scripts/zhusque-browser.js`。

浏览器使用持久的专用可见窗口，不使用用户个人 Chrome 配置，也不每轮创建无痕窗口。macOS 默认配置目录为 `~/Library/Application Support/ruanzhu-kit/zhusque-browser`。

### 3.1 兜底的触发和能力边界

浏览器连接或接管失败、页面定位器失效、点击无效、遮挡弹窗、验证码、登录页、结果等待超时，均须保留当前窗口和进度，交给具备 Computer Use 的宿主 agent 判断下一步。执行本 Skill 的 agent 必须先检查已有 Computer Use 工具并在可用时实际尝试，不能看到这些状态就一律要求用户手工完成。

Computer Use 由 Codex/Claude 等宿主提供，当前 agent 直接调用。Python/Node 脚本退出并保存 `pending_computer_use` 后，agent 应立即读取当前记录，继续下面的操作流程，不能仅展示交接文件便结束任务。只有没有可调用工具时，才保留 pending、已有窗口和交接记录，说明“当前运行环境没有 Computer Use 工具”。网页驱动缺少 Playwright 等依赖时，宿主 CUA 仍可检查可见浏览器并协助操作；能否将结果自动读回必须单独验证。

### 3.2 交接文件和续检入口

发生可接管的失败时，材料目录内会生成：

- `朱雀复核/computer-use-handoff.json`：当前机器可读交接，包含失败原因、原文路径与 SHA-256、来源文件/行号、官方 URL、浏览器配置目录、证据路径、提交凭据及 `resume_argv`。
- `朱雀复核/Computer-Use接管说明.md`：供 agent 和用户阅读的当前操作说明。
- `朱雀复核/待检文本/<SHA-256>.txt`：本次单元的完整 UTF-8 原文，必须与交接中的 `text_sha256` 一致；不是整份文档，也不包含 API Key。
- `朱雀复核/接管记录/<handoff_id>.json`：历史交接记录，用于追溯状态和证据。

上述文件为本地内部复核材料，原文和交接文件按仅当前用户可读写的权限保存，不随软著提交件上传。脚本还会输出以 `RUANZHU_COMPUTER_USE_HANDOFF ` 开头的 JSON 事件，便于宿主发现待接管工作；看到事件不代表工具已被调用。

只有 `status=pending_computer_use` 是当前待操作任务。`blocked_quota` 表示额度限制；`stale` 表示材料已变化，不能继续按旧原文操作；`resolved` 表示对应结果已通过正常检测或 CUA 导入校验，整份材料仍以 `finalize` 为准；历史记录中的 `superseded` 表示已被新的交接替代。操作前重新读取当前记录，不能盲目重放旧交接。

`pending_receipt` 提供提交凭据的路径、是否存在、身份是否匹配、提交阶段及 `submission_may_have_occurred`。该字段为真或页面提交状态不明时，先核实原提交，不能删除凭据后强行重发。`actions` 列出允许操作以及提交前必须核实的条件。

`resume_argv` 是程序与参数组成的列表，可直接作为进程参数使用，不是可拼接执行的 shell 字符串。它保留检测范围、渠道和阈值，并刻意不携带 `--no-cache`，以免恢复时重测已完成内容。也可继续执行第 2 节的普通增量命令。网页驱动优先正常回读结果；只有宿主 CUA 已从真实结果页取得完整分类 DOM 时，才使用第 3.4 节的校验导入，不能手填截图比例或任意结果 JSON。

### 3.3 宿主 agent 的必做步骤

1. 读取本次交接记录，核对材料路径、待检原文和哈希、官方 URL、失败原因、页面证据、提交凭据及续检参数。只处理既定材料，不把 API Key、账号信息或交接文件全文贴进检测框。
2. 按宿主工具说明取得当前浏览器/应用状态，优先绑定保留下来的专用窗口和官方检测标签。不要硬编码旧 tab ID，不新建窗口来丢弃当前验证码或提交状态。如果专用窗口确实不在宿主可控范围，可使用另一个可控的官方检测页，但只处理已核实尚未提交的单元；已提交或状态不明的单元继续保留原现场，不能换窗口重发。接管后先读实时截图和可见控件，确认当前处于输入、验证码、检测中还是结果页。
3. 对已观察到的控件执行点击或输入操作（验证码除外）。能使用可见控件定位时优先定位；必须点坐标时，只使用当前截图中实际可见的位置，界面变化后重新读取，不能猜坐标、沿用失效位置或连续盲点。弹窗遮挡、按钮未响应和焦点错误应各自修复，不能直接反复点“检测”。
4. 出现验证码或登录页时停止操作，请用户本人在当前窗口完成；agent 不代解验证码，也不以“用户已授权”为由代为完成。用户确认完成后，查看页面状态再继续。
5. 保持同一原文和提交凭据。已有待完成提交时先等待或恢复其结果；若同一页面仍保留匹配凭据且结果全文对应，可以恢复结果，不重新提交。不能把首页演示文本、旧的其他文本结果或只显示比例的截图当成本次完整检测。页面重载或提交凭据丢失时，先核实状态；无法关联则保持 pending，不靠重复提交碰运气。
6. 保存必要的实际操作和结果证据，按交接记录中的命令恢复检测。网页驱动无法读回但宿主已取得完整分类 DOM 时，先按下一节校验导入。续检仍按缓存和文本指纹只处理未完成、新增或变化单元。只有结果与本次原文对应且覆盖完整，才能更新检测完成状态。

CUA 只负责把当前页面操作推进到可核验状态，不能通过改本地标签、补造分类或把截图解读成 API 返回值来使检测通过。若只能读到截图上的总分而不能取得完整分类正文，保留页面和证据并准确报告“可见结果已取得、完整分类数据未取得”，不伪造导入成功。

### 3.4 完整 CUA 分类结果的校验导入

当宿主 CUA 已实际操作官方检测页面，并从该次真实结果的 DOM 读取全部分类片段时，可以执行：

```bash
python3 <skill目录>/scripts/zhusque_handoff.py import-cua-result <材料目录> <capture.json>
```

`capture.json` 必须来自实际页面观察，包含：

- `source` 固定为 `computer_use_live_dom`，`url` 为 `https://matrix.tencent.com/ai-detect/`。
- `request_id`、`submitted_text_sha256` 与当前交接单元一致；`captured_at` 为带时区的 ISO 时间。
- `segments` 为完整分类数组，每项含真实片段 `text` 和整数 `label`：`0` 人工、`1` AI、`2` 疑似。
- `evidence` 至少包含一个真实、非空本地文件的绝对路径，键名为 `screenshot`、`page_record` 或 `accessibility_record`；截图只能作为证据，不能替代完整分类正文。

导入仅接受当前 `pending_computer_use` 交接。脚本重新核对材料清单指纹、待检原文 SHA-256、请求标识、官方 URL、采集时间和证据文件，并确认所有分类片段拼接后与原文去除空白逐字一致，然后自行计算字符占比和片段位置写入网页缓存。材料已修改、分类不全、原文不一致或证据缺失时拒绝导入，不接受调用方给出的总分来替代计算。

文件格式和本地校验无法证明真实的浏览器操作过程，宿主必须保留实际 CUA 工具调用与页面证据，不能自己编造 `segments`。导入成功只表示该单元进入缓存；它不会写整份材料的完成标记。随后执行返回的 `resume_argv` 或普通 `finalize`，由增量流程核验其余正文的覆盖和阈值。

### 3.5 额度与中断后的续检

- **额度不足**：保存成功结果和未完成状态，等待额度恢复或使用另一个已配置且有额度的正式渠道。Computer Use、清缓存或重开无痕窗口都不能作为额度已恢复的证据。
- **验证码、登录或界面操作暂未完成**：保留专用窗口、原文、提交凭据与成功缓存，完成必要的 CUA 操作后按交接记录续检。
- **结果无法关联或页面仍不可用**：保存可用证据，保留未完成状态，不用本地分数填补网页结果。

`--browser-timeout` 可调整网页单次等待时间。一次阻塞不要求重新发送已成功的全部正文；只有显式 `--no-cache` 才强制重测。

**验证记录须分开说明：已接管窗口、已点击控件、用户已完成验证码、已取得本次真实检测结果、结果已导入。** 其中任意前一步都不能替代后一步。解析器和流程的离线回归不能证明线上完整检测已通过；实际报告必须据本次取得的结果记载。

2026-09-24 的现场验证使用用户说明书“软件概述”的第 2 个单元，共 596 字符。原脚本专用 Chrome 没有可供宿主 CUA 绑定的窗口，因此改用现有可控的朱雀 IAB 页面；先确认该第 2 单元尚未提交，再清除网页样例、填写、提交并回读真实结果，没有重发原窗口中的第 1 单元。页面返回 `Strong human creation`，可见段分为 `0.2118`；该段分按页面显示记载，不当作全文 AI 占比。完整 DOM 分类数据已校验导入，随后 `finalize` 命中 1 个缓存、新增请求 0 次、API Token 0，并通过该单元复核。

验证码由用户本人完成，agent 不代解。此次也没有修改或全量复检用户原始整套材料，单元验证不代表整套材料已通过。

## 4. 读懂报告和用量

`朱雀检测报告.md` 展示当前覆盖字符数、待检位置、缓存和本轮请求、API/网页来源，以及 API 返回的 `makers_models_usage.total_tokens`。网页检测不产生 API Token 记录；API 失败请求是否计费不能从本地成功结果推断。

全文比例是当前全部检测单元对应的历史有效结果与新结果按字符量加权汇总，**不是本轮单次重新提交了全文**。网页从可见分类片段计算的结果也要保留来源说明。报告没有完整覆盖时，只能描述已检测部分，不能宣称全文通过。

文档页数不等于请求量。实际请求取决于提取字符量、分块和缓存命中；PDF 排版、图片占比及 Markdown 语法都会影响字符量。`--plan` 的字符量可用于预算，实际用量以服务返回字段为准，不把某次观察到的字符/Token 比例当作官方固定公式。

`finalize` 只有在当前选定文本覆盖完整、结果仍对应当前材料且 AI＋疑似比例不超过阈值时才写 `.zhusque-final.json`。`--max-risk-ratio` 默认且最高为 0.20，只能调低不能调高；材料核验也固定按 0.20 判定，不采信标记中记录的阈值。0.20 是项目复核规则，不是腾讯、版权登记机构或法律的标准。请求失败、覆盖不足或风险超限不能留下可用的通过状态。上传前仍需通过 `artifact_manifest.py --verify --strict` 的材料核验。

## 5. 按任务单改写，再增量复核

`朱雀改写任务单.md` 只列出被标为 AI/疑似的单元；有可靠段内位置时给出对应原文，没有时明确列出整个单元供复核。任务单不会解释模型未返回的判定原因，也不会生成可直接当事实使用的替换文案。

1. 根据源码、真实界面和操作记录核对标记内容，补足真实的操作、输入、响应或异常条件；没有依据就删掉空泛描述，不编造功能或实验结果。
2. 以 `软件说明书.md` 为正文主版本，只改任务单及用户要求的范围，同步 `说明书章节/` 中受影响部分。申请表修改须同步对应配置与文案，不能留下与主版本脱节的“优化版”。
3. 当前 agent 按材料生成流程重新渲染已有 PDF，然后运行 `finalize`；新 PDF 提取文本变化的单元也纳入增量计划。
4. 检查本轮覆盖、实际用量和改前改后结果。修改没有保证降分；仍超阈值时如实列出剩余问题，不靠循环改写全文或改检测标签伪造通过。

本地 `AIGC检测报告.md`、朱雀报告、改写任务单、进度文件和网页证据均为内部复核材料，不随说明书/源码 PDF 自动上传版权登记网站。
